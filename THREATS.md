# THREATS.md — Threat Model, Mitigations & Accepted Risks

This document analyzes how an attacker, malicious insider, or judge could attempt to break **TrustVault**, the concrete server-side controls implemented to close each attack vector, how those controls are verified by automated tests, and the residual risks we knowingly accepted within the 7-day build window.

---

## 1. Threat Matrix & Implemented Controls (STRIDE)

| **T6** | **Unaudited Actions (Fail-Open Auditing)**<br>Attacker triggers an audit failure (e.g., database error or corrupted chain) hoping the application will still log them in, save their file, or grant permissions without leaving an audit trail. | • **Fail-Closed Transaction Design:**<br>  - If login auditing fails, `login_user()` is never called (`503`).<br>  - If registration, upload, edit, share, or revoke auditing fails, the database change is rolled back/compensated and physical files are unlinked or restored to their previous bytes.<br>  - If deletion pre-request auditing fails, deletion does not start; if post-delete final auditing fails, the document **stays inaccessible** (fail-safe). | `app/auth.py`<br>`app/documents.py`<br>`tests/test_auth_audit_failures.py`<br>`tests/test_documents.py`<br>`tests/test_sharing.py` |

| **T8** | **Denial of Service via Oversized Uploads & Race Conditions**<br>Attacker uploads a multi-gigabyte file to exhaust disk/RAM or fires concurrent requests to corrupt `CHAIN_INDEX`. | • **Hard Payload Limits:** `MAX_CONTENT_LENGTH = 16 * 1024 * 1024` (16 MiB) enforced by Flask/Werkzeug before reading the stream; browser text editor capped at 1 MiB.<br>• **Exclusive Table Lock:** `LOCK TABLE TV_AUDIT_LOGS IN EXCLUSIVE MODE` serializes concurrent audit writes. | `config.py`<br>`app/documents.py`<br>`tests/test_documents.py` |

## 2. Residual Risks Knowingly Accepted & Why

Per the challenge instructions (*"An entry saying 'I know this is weak and here is why I left it' is worth marks"*), here are the weaknesses we knowingly accepted in this 7-day build and how we would close them in production:

1. **Full-ChainRecomputation by a Privileged Database User (`DB_USER`):**
   * **The Weakness:** Because `append_audit_event()` uses an unkeyed SHA-256 hash (`_canonical_hash`) and the application's database connection (`DB_USER`) has `UPDATE`/`DELETE` privileges on `TV_AUDIT_LOGS`, an attacker who compromises the database credentials (or a rogue DBA) could alter row 1 and recompute `PREVIOUS_HASH` and `EVENT_HASH` for all subsequent rows `1..N` so `verify_audit_chain.py` still passes.
   * **Why We Accepted It:** Setting up multi-schema Oracle privilege separation or external KMS signing was out of scope for a single-schema local/cloud Oracle XE deployment.
   * **Production Fix:** (a) Use an Oracle **Immutable Table** or revoke `UPDATE`/`DELETE` on `TV_AUDIT_LOGS` from the app user (`GRANT SELECT, INSERT ONLY`), (b) replace SHA-256 with `HMAC-SHA256` using a key stored in HSM/KMS outside the database, and (c) stream each `EVENT_HASH` to an external WORM log (e.g., S3 Object Lock).

2. **$O(N)$ Audit Lock Contention & Login Audit DoS:**
   * **The Weakness:** Every call to `append_audit_event()` locks `TV_AUDIT_LOGS` in exclusive mode and reads all existing rows (`_load_and_validate_chain`) to verify the entire chain before inserting. Furthermore, failed `/login` attempts also write to the audit log without IP rate-limiting. An attacker flooding `/login` with bad passwords can cause lock contention and $O(N)$ database CPU exhaustion.
   * **Why We Accepted It:** We prioritized strict fail-closed consistency and immediate tamper detection on every write over high-throughput concurrency.
   * **Production Fix:** Validate only the latest tail row (`WHERE CHAIN_INDEX = (SELECT MAX(...) FOR UPDATE)`) synchronously during the request ($O(1)$), move full-chain verification to an asynchronous background job, and add `Flask-Limiter` rate-limiting on `/login` and `/register`.

3. **Unencrypted Files at Rest on Local Disk (`instance/private_uploads/`):**
   * **The Weakness:** While files are unreachable over HTTP without authorization, they are stored as raw bytes on the server's filesystem. An attacker who gains host OS root/filesystem read access could read files directly from `instance/private_uploads/` without triggering the application audit log.
   * **Why We Accepted It:** Application-layer envelope encryption (AES-256-GCM per document with keys managed via KMS) was traded off to keep streaming downloads and in-browser text editing simple and reliable within the 7-day window.
   * **Production Fix:** Encrypt each file before writing to disk using `cryptography.hazmat.primitives.ciphers.aead.AESGCM` with a unique per-document Data Encryption Key (DEK) wrapped by a Master Key in KMS.

4. **Extension & UTF-8 Validation Rather Than Deep File-Signature (Magic-Byte) Inspection:**
   * **The Weakness:** Upload validation sanitizes filenames (`secure_filename`), enforces the 16 MiB size limit, and always serves downloads with `as_attachment=True` (`Content-Disposition: attachment`) so uploaded HTML/SVG files cannot execute XSS in the browser. However, the server does not inspect file magic bytes (`libmagic`) or scan for malware payloads.
   * **Why We Accepted It:** Serving all downloads strictly as attachments (`as_attachment=True`) neutralizes stored XSS via file upload, and avoiding C-library `libmagic` dependencies kept cross-platform deployment clean.
